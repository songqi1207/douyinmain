## 1. 结论

平台正式作品基线是 **23 条**，但不能把 R2 最近的 23 个文件名前缀直接当成 23 条作品。只读审计确认：

- R2 有 112 个媒体对象，共约 2.95 GB，按导出名前缀归为 42 组。
- 最近一段有 23 个前缀，其中包含同一任务的重新导出、修复测试、替换前版本和一个乱码测试。
- 新服务器目前没有这批历史作品关联：`video_storage` 为 0，任务库也不是旧生产库的完整副本。
- 视频文件仍在 R2，当前主要缺失的是旧 `jobs`、`video_storage`、所属用户和草稿 JSON 的准确关联。

因此，本清单先锁定所有候选文件与替换关系；在 23 条逻辑作品最终核对完成前，不删除任何 R2 对象，也不把测试前缀批量写入新数据库。

## 4. 数据库恢复约束

1. 先备份新服务器的两个 SQLite 数据库。
2. 只使用 `INSERT ... ON CONFLICT DO UPDATE` 合并历史记录，不覆盖新服务器现有用户和任务。
3. 重新导出任务不得新增一条“我的作品”；应更新原任务的 `results_json` 和 `video_storage`。
4. `DRAFT_KEY_EXPORT`、`godanim`、`godfull` 等技术导出任务默认不单独显示为作品。
5. 乱码测试、失败任务和修复中间件管理员可查，但普通用户作品页不显示。
6. 恢复后普通用户应看到 23 条逻辑作品；管理员可额外看到失败任务和修复过程记录。
7. 23 条正式作品全部核对之前，禁止清理 R2、旧导出机缓存和旧日志。
